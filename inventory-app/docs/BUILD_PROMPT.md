# برومبت تنفيذ مشروع "تطبيق الجرد" (Inventory Audit App) — من A إلى Z

## 1. نظرة عامة على المشروع

ابنِ **نظام ويب + تطبيق موبايل** لتنفيذ عمليات الجرد (Inventory Audit) داخل
الشركات. النظام يخدم ثلاثة أطراف رئيسية:

1. **الأدمن (Admin)**: يدير حساب الشركة، الموظفين، الأصناف، المستودعات،
   ويسند مهام الجرد، ويراجع النتائج.
2. **الموظف (Employee)**: ينفذ الجرد ميدانياً عبر تطبيق الموبايل بمسح
   الباركود.
3. **المراجع (Reviewer)** (اختياري): يراجع نتائج الجرد قبل الاعتماد النهائي،
   خصوصاً عند وجود فروقات كبيرة.

## 2. المتطلبات الوظيفية الكاملة

### 2.1 إدارة الحسابات والصلاحيات
- إنشاء حساب خاص بكل شركة بكلمة مرور مخصصة للأدمن.
- الأدمن يضيف الموظفين، يعرّف الأصناف والباركود، يعرّف المستودعات/الأقسام/
  أماكن التخزين، ويحدد صلاحيات كل مستخدم (RBAC + نطاق وصول على مستوى
  المستودع: قائمة `warehouseScope`، فارغة = وصول لكل المستودعات).
- الأدوار: `ADMIN`, `EMPLOYEE`, `REVIEWER`.

### 2.2 لوحة تحكم الأدمن
- تقارير لحظية دقيقة لحركة المخزون وتنبيهات بالنواقص.
- واجهة مستخدم سهلة الاستخدام، تدعم الوضع الداكن وتعدد اللغات.
- تكامل مستقبلي مع منصات التجارة الإلكترونية (مرحلة لاحقة، غير مطلوب في
  MVP).

### 2.3 إدارة الأصناف والوحدات
- كل صنف له باركود، اسم، سعر، مورد، فئة، ورصيد نظري (`systemQty`).
- دعم وحدات متعددة للصنف الواحد (مثال: قطعة = الوحدة الأساسية، صندوق = 24
  قطعة، كرتونة = 12 علبة). عند اختيار الموظف لوحدة غير أساسية، **تعبئة
  الكمية الأساسية إجبارية** (مثال: صندوق × 24 قطعة). السماح/المنع من
  استخدام وحدات أكبر من الأساسية يكون بيد الأدمن.
- تزويد النظام بالأصناف والكميات عبر:
  - رفع ملف CSV أو Excel.
  - أو الربط المباشر مع قاعدة بيانات خارجية وتنفيذ استعلام مباشر لجلب
    البيانات (يُبنى كموديول استيراد قابل للتوسعة، منفصل عن استيراد CSV).

### 2.4 آلية إسناد الجرد
- الأدمن يختار الموظف أو مجموعة الموظفين المسؤولين، ويسند لكل موظف:
  - الأصناف أو مجموعة المواد العامة أو مواد مورّد معين (`scopeType`:
    `ALL` | `CATEGORY` | `SUPPLIER` | `ITEM_LIST`).
  - المستودع/القسم/الفرع المطلوب جرده.
  - ساعة بدء المهمة.
- إشعار فوري يصل للموظف بتفاصيل المهمة والتعليمات (Push Notification —
  انظر القسم 2.9).

### 2.5 تنفيذ الجرد (تطبيق الموبايل)
- الموظف يحدد موقع الجرد بدقة (مثال: داخل المستودع - الواجهة رقم 1 -
  صالة رقم 5).
- المسح عبر كاميرا الموبايل أو قارئ باركود خارجي (سلكي/لاسلكي).
- **وضع المسح السريع المتواصل**: تمرير القارئ بسرعة متتالية دون الحاجة
  للنقر على الشاشة في كل مرة، مع نغمة صوتية إيجابية للقبول ونغمة مميزة
  عند الخطأ.
- **الجرد الأعمى (Blind Count)**: خيار بيد الأدمن لكل مهمة — إخفاء الرصيد
  الفعلي المسجل بالنظام عن الموظف أثناء العد.
- عند مسح باركود مادة غير مسجلة:
  - يصدر صوت تنبيه.
  - يظهر خيار لتسجيل المادة: صورة المنتج + صورة الباركود + اسم المادة +
    السعر + الكمية الموجودة.
  - المادة الجديدة تظهر في جدول خاص للأدمن لاعتمادها أو رفضها مع متابعة
    سبب عدم وجودها في قاعدة البيانات.
- إمكانية تحديد **حالة خاصة للمادة** (مثلاً: تالف) مع إرفاق صورة إلزامية
  في هذه الحالة.
- عند مسح باركود المادة، تُسجَّل بكمية 1 ويستعد النظام لمسح المادة
  التالية مباشرة، مع إبقاء **آخر 5 حركات** ظاهرة على الشاشة، وإمكانية:
  - تعديل الكمية عبر زر (+) أو (-) بجانب كل حركة.
  - أو الضغط على سطر المادة لفتح كامل تفاصيلها وتحريرها.
- **تجميع الكميات**: خيار بيد الأدمن لكل مهمة — تجميع الكميات تلقائياً
  عند مسح المادة في مواقع مختلفة (Aggregate)، أو تركها متسلسلة حسب
  الإدخال (Sequential) لتسهيل التدقيق ومعرفة الزيادات بدقة مكانية.
- عند انتهاء الجرد: تقرير مفصل يشمل جميع النواقص والمواد المضافة حديثاً.

### 2.6 الفوارق وإعادة العد
- **إظهار/إخفاء الفوارق** عند نهاية الجرد: خيار بيد الأدمن لكل مهمة.
- **إعادة العد التلقائي**: إذا تجاوز الفرق نسبة تفاوت محددة، يصدر النظام
  طلب إعادة عد أو يحوّل المهمة لمراجع ثانٍ. النسبة قابلة للتحديد:
  - نسبة عامة على مستوى المهمة (`generalRecountTolerancePct`).
  - أو نسبة خاصة بصنف معين (`recountTolerancePct` على مستوى الصنف)،
    ولها أولوية على النسبة العامة.

### 2.7 العمل بدون اتصال والمزامنة (Offline & Sync)
- التطبيق يعمل بدون اتصال بالكامل أثناء الجرد.
- كل عملية جرد تُخزَّن في **جدول مخصص Append-Only** (لا تُعدَّل الصفوف
  أبداً، فقط تُضاف) يحوي: رقم الموظف، التاريخ، رقم المهمة، وبقية بيانات
  الجرد الفعلي (الباركود، الموقع، الوحدة، الكمية، الحالة...).
- عند عودة الاتصال: يتم رفع دفعة الجرد المخزنة محلياً دفعة واحدة، مرتبطة
  تلقائياً بحساب الموظف الذي نفّذ الجرد (عبر التوكن، وليس عبر حقل يُرسل
  من الجهاز، لمنع التلاعب).
- **تعارض المزامنة (Conflict Resolution)**: يُحل عبر التصميم الـ
  Append-Only نفسه + الطابع الزمني الدقيق لكل مسحة وموقع (`deviceTimestamp`)
  — لا يوجد تعديل مباشر على حقل إجمالي، فلا يوجد فقدان بيانات عند عمل
  أكثر من موظف بدون اتصال في نفس الوقت.
- بعد المزامنة، يقوم الأدمن أو المعتمد بتوليد **تقرير نهائي تجميعي** من
  كل السجلات المرتبطة بالمهمة، ثم تصديره أو مزامنته مع برنامج المحاسبة
  أو كملف CSV.

### 2.8 متطلبات تقنية عامة
- قاعدة بيانات: **PostgreSQL**.
- دعم مزامنة سحابية فورية عبر أجهزة متعددة.
- حماية بيانات متقدمة (تشفير كلمات المرور، JWT، صلاحيات محكمة).
- أداء سريع ومستقر في جميع ظروف التشغيل (خصوصاً أثناء المسح السريع
  المتواصل).
- تحديثات دورية وقابلية للتوسع لإضافة ميزات جديدة.

### 2.9 إشعارات
- إشعار فوري للموظف عند إسناد مهمة جرد جديدة له بكل التفاصيل والتعليمات.
- إشعار فوري للأدمن/المسؤول المباشر عند نواقص حرجة أو طلب إعادة عد.
- نظام إشعارات ذكي للتفاعل اللحظي (Push Notifications عبر Firebase Cloud
  Messaging أو ما يعادله).

### 2.10 دعم فني ولغات
- دعم فني دائم للعملاء (قناة تواصل داخل التطبيق أو خارجية — تُحدَّد لاحقاً).
- دعم تعدد اللغات (i18n) من التصميم الأول للواجهة، حتى لو بدأ الإطلاق
  بلغة واحدة.

## 3. الأولويات والنطاق (Scope) المتفق عليه للبناء الحالي

**مُدرج في البناء الحالي (المرحلة 1 + 2):**
- كل ما ورد في القسم 2 عدا ما استُثني أدناه صراحة.

**مؤجل/خارج النطاق حالياً (لا تبنِه إلا إذا طُلب صراحة):**
- دعم الباركود المركب GS1-128 وحقول Batch/Lot/Expiry.
- تكامل منصات التجارة الإلكترونية.
- شاشات لوحة تحكم الويب الكاملة (Frontend) — التركيز الحالي على الـ API
  والموبايل.
- الدعم الفني الحي (Live chat/ticketing).

## 4. الحل التقني المطلوب

| الطبقة | التقنية |
|---|---|
| الباك-إند | Node.js — Express (أو NestJS) |
| قاعدة البيانات | PostgreSQL عبر Prisma ORM |
| المصادقة | JWT + bcrypt |
| تطبيق الموبايل | React Native (Expo) — Android + iOS من كود واحد |
| الاستضافة | Docker + docker-compose على سيرفر Oracle Cloud الحالي لدى العميل |
| التصدير | CSV (كحل أولي قبل تكامل محاسبي مباشر) |

### آلية المزامنة المتفق عليها بالتفصيل
1. كل حركة جرد تُخزَّن محلياً في طابور (Queue) على الموبايل فور مسحها.
2. عند توفر الاتصال، يُرفع الطابور دفعة واحدة إلى `POST /audit-records/sync`.
3. كل سجل في جدول `AuditRecord` يحمل: `employeeId` (من التوكن)، `taskId`،
   `deviceTimestamp`، وبيانات الجرد الفعلية — ولا يُعدَّل أي سجل قائم أبداً.
4. توليد التقرير النهائي هو خطوة منفصلة يقوم بها الأدمن/المراجع، تجمّع كل
   السجلات المرتبطة بالمهمة وتحسب الفروقات، ثم يُصدَّر كملف CSV أو يُزامن
   مع برنامج المحاسبة.

## 5. معايير القبول (Definition of Done) لكل ميزة

- [ ] يمكن للأدمن إنشاء حساب شركة وإضافة موظف بصلاحيات محددة.
- [ ] يمكن استيراد أصناف عبر CSV مع وحدات متعددة إجبارية الكمية الأساسية.
- [ ] يمكن إسناد مهمة جرد بكل خياراتها (Blind Count، تجميع/تسلسل، نسب
      إعادة العد).
- [ ] يعمل تطبيق الموبايل بدون اتصال بالكامل، ويزامن تلقائياً عند عودة
      الاتصال دون فقدان أي حركة.
- [ ] مسح باركود غير مسجل يُنتج تنبيهاً صوتياً وخيار تسجيل بصورتين.
- [ ] تقرير نهائي يُظهر الفروقات (أو يخفيها حسب إعداد الأدمن) ويُصدَّر CSV.
- [ ] أي صنف يتجاوز فرقه النسبة المحددة (عامة أو خاصة به) يُعلَّم لإعادة
      العد تلقائياً.

## 6. تعليمات للوكيل الذكي عند التنفيذ

1. ابدأ دائماً بمخطط قاعدة البيانات (schema) كاملاً قبل كتابة أي endpoint.
2. اجعل جدول حركات الجرد **Append-Only** بدون استثناء — أي "تعديل" هو
   سجل جديد، وليس UPDATE على سجل قائم.
3. لا تدمج منطق حساب الفروقات وإعادة العد داخل الراوت مباشرة — اعزله في
   دالة/موديول مستقل قابل للاختبار.
4. لا تبني ميزات القسم "مؤجل" أعلاه إلا إذا طُلب ذلك صراحة.
5. وثّق كل endpoint وكل قرار معماري في README مرافق.
6. عند الشك في تفصيل غير محسوم، اسأل بدلاً من الافتراض.
